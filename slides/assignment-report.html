一LLM Wiki 主題與簡介

主題是「大型語言模型（LLM）＋ 強化學習（RL）應用於無人機」。這是一個很新的交叉領域：LLM 擅長看全局、懂語言，但慢又會幻覺；RL 反應快，但視野小。這個 wiki 長期追蹤「兩者怎麼分工」的論文。

建置方式參考 Karpathy 的 LLM Wiki 模式，分工如下：

👤 我負責

  • 決定主題範圍與方向
  • 蒐集論文、把 PDF 放進 raw/inbox/
  • 提問、決定下一批要追什麼文獻

🤖 LLM（Claude Code）負責

  • 閱讀 PDF、寫摘要頁
  • 交叉連結概念、任務、實體頁
  • 維持一致性：矛盾、斷鏈、分類檢查
先討論、後生成：動手前先討論並決定了主題範圍、正文語言（繁中、英文檔名）、批次匯入方式、論文分類法和簡報風格，寫成規則檔 CLAUDE.md（schema），之後所有頁面都照這份規則產生。做簡報時也是先討論：先寫 需求單（需求摘要），確認後才開始。

四Loop / Graph 設計

整個流程分成三條線：建立規則（只做一次，必要時回頭修改）、匯入迴圈（每批論文跑一次）、簡報產生（每次要做簡報時跑一次）。簡報產生這條線是改版後的 graph：每個節點產出一個檔案，每個檔案後面接一個檢查站。

正常流程重複／退回檢查節點（黃底含使用者確認 G；粗框 ②③ 是改版後新增的節點）

🔁 哪些步驟會重複？

  • 匯入 ②③ 每篇論文都跑一次；①～⑧ 每一批跑一次，⑧ 決定追哪些引用文獻再回到 ①
  • 簡報 ⓪～⑤ 每做一份簡報跑一次
  • 任何檢查站沒通過，就從被退回的節點往下重跑，上游的檔案不動

🔍 哪裡要檢查或重新產生？

  • C1：wiki 缺頁 → 先回匯入迴圈補頁
  • C2／G2：結構問題（一頁講兩件事、名詞沒解釋）→ 改 ② 大綱
  • C3／G3：數字不在 wiki、說法比 wiki 強 → 改 ③；wiki 本身有錯 → 回 wiki
  • C4／G4：HTML 出現 ③ 沒有的字 → 回 ③；版面問題 → 留在 ④

💡 為什麼這樣設計？

  • 結構和內容分開確認：順序錯和數字錯是兩種問題，應該在不同的節點被攔下
  • 一個節點一個檔案：出錯時只要改那個檔案和它的下游
  • HTML 只能用 ③ 的文字：用腳本強制，內容錯誤就不可能在最後一步才混進來

五一次實際執行的紀錄

以下是用 graph 流程產生入門教學版簡報的那一次執行，完整紀錄見 檢查紀錄。

  1. ⓪ 需求單 → G0：寫下對象（沒學過 RL 的同學）、時長（約 15 分鐘）、聽完要記住的三件事。我確認後才往下做。
  2. ① 素材表 → C1：從 wiki 挑出 15 筆素材。腳本確認引用的 wiki 頁都存在、所有數字都在 wiki 裡（0 缺）；這次不需要補頁。
  3. ② 大綱 → C2 → G2：19 頁、每頁一句重點。自查抓到 3 處：「LLM 上機的難題」那頁原本講三件事、用了外行聽不懂的名詞（embedding、CMDP）、多一頁名詞辭典。→ 在 ② 內修正，我確認大綱。
  4. ③ 逐頁內容 → C3 → G3：腳本確認 23 個數字、7 筆參考文獻都對得上。人工核對抓到 3 處說得比 wiki 更強：「樣本效率」被寫成「速度」、多了一個 wiki 沒有的「反而」、「2D 設定」被擴大到全部論文。→ 在 ③ 內修正，我按章節確認。
  5. ④ HTML → C4：腳本確認 HTML 上 240 段文字都在 ③ 裡（另外故意塞一句假數字，確認腳本抓得到）。三輪截圖抓到 5 處版面問題：字太小，以及 4 處重疊或換行。→ 在 ④ 內修正。
  6. G4 我預覽：要求封面加上作者。→ 依規則退回 ③ 先加字，再改 HTML，文字比對 241/241。
  7. ⑤ 發布：定稿，在 log.md 追加紀錄、commit。

六反思

Q1. 哪一個節點最常出錯？

產生簡報內容的節點。錯的不是版面，而是內容偏離 wiki：

  • 第一份簡報（文獻導讀）：MAPPO 那頁把 CI-HRL 的說法寫錯，參考文獻標題是憑印象改寫的
  • 第一版教學簡報：把「只用 LLM 多耗 58%」說成「幻覺造成 58%」
  • 這次的 graph 版：在 ③ 又抓到 3 處，例如把「樣本效率」寫成「速度」

共同原因：LLM 寫簡報時會改寫、簡化原文，改寫時容易把說法變強或變形。教學簡報要用比喻、要白話，這個風險更高。三次都是同一類錯誤，所以這是這個節點固有的問題，不是偶發失誤。

次常出錯的是匯入時的分類節點 ③：第一批 8 篇裡有 5 篇放不進原本「LLM+RL+UAV」的框架。

Q2. 發現問題後，把檢查往前移到哪一步？

移了兩次：

  • 第一次（第一版教學簡報）：從「做完 HTML 再看」移到寫之前的出處對照表，並加上數字自動比對。
  • 第二次（這次的 graph 版）：把「寫簡報」拆成 ② 大綱 和 ③ 逐頁內容 兩個節點，各自設檢查站和我的確認。內容的核對全部在 ③ 完成，HTML 之前就結束。

結果：

  • 第一份簡報：做完才發現 2 類內容錯誤。
  • 第一版教學簡報：1 處內容錯誤，在 HTML 完成後的人工核對才抓到。
  • graph 版：3 處內容錯誤，全部在 ③ 就攔下，HTML 階段只剩版面問題。
Q3. 有沒有因此修改 workflow / graph？為什麼？

有。簡報產生從一條直線（查 wiki → 寫 HTML → 檢查 → 回頭重寫）改成上圖的分段 graph：

  • 每個節點產出一個檔案：需求單、素材表、大綱、逐頁內容、HTML。要改哪一層，就只改那個檔案和它的下游。
  • 回饋依層級退回：結構問題回 ②、內容問題回 ③、版面問題留在 ④。這次我要求加作者，就是照這條規則先回 ③。
  • HTML 只能使用 ③ 的文字：用腳本 check_deck_text.py 強制執行。

原因：舊流程的檢查集中在最後，一發現錯就要整份重做，而且結構錯誤（頁面順序、一頁講太多）和事實錯誤混在一起。分段之後，結構由大綱把關、事實由逐頁內容把關、外觀由 HTML 把關，每種錯誤都在最便宜的地方被攔下。

匯入流程也改了兩處：

  • 加上「分類不合 → 改 schema」的回頭路。
  • 每批匯入後固定跑連結檢查，因為斷鏈是 LLM 自己編出頁面名稱造成的。

設計原則：能用程式檢查的就用程式（數字、連結、HTML 文字），需要判斷的才用人工（說法強度、分類、結構）。

還沒解決的部分：
  • C3 的「說法強度」仍要靠逐條人工核對，沒有自動化。
  • wiki 本身的正確性仍取決於閱讀 PDF 的品質。目前會在論文頁標註「待確認」，但沒有回頭抽查原文的固定步驟，這是下一個可以補的檢查節點。
